## Итерация 17 — восстановление `/offerstatus` (08.09.2026)

- `/offerstatus` больше не пытается отправлять эскалацию в канал перед формированием ответа: ошибка Telegram-канала не может оставить команду без ответа. Ошибка чтения статистики ловится и записывается в журнал.
- `process_expired_offer_campaigns` изолирует ошибку каждой заявки, поэтому одна недоставленная эскалация не останавливает планировщик и остальные опросы.
- Для сообщения эскалации добавлен резервный plain-text вариант: если Telegram отклоняет HTML с упоминаниями, бот повторяет отправку обычным текстом. Эскалация считается доставленной только после успешной отправки.

## Итерация 16 — надёжное завершение опроса (08.09.2026)

- `process_expired_offer_campaigns` запускается отдельным проходом в начале `run_checks`: опрос завершается по `admin_offers.sent_at`, даже если у заявки отсутствует/изменён `created_ts` и она больше не попадает в исходную 36-часовую ветку.
- При снятии куратора с заявки, возвращённой в `new`, старые `admin_offers` и `offer_escalations` очищаются. Защитная очистка старого ответа `yes` есть и при старте следующего опроса, поэтому предыдущая попытка кураторства больше не удерживает заявку.

## Как всё устроено

### Фронтенд (prototype/index.html + prototype/style.css)
- `SCREENS` — объект экранов, `stack`+`render()` — навигация. `SRV` = ответ бэкенда (null → демо на моках). `api(path,body)` шлёт POST /api/… с `initData`; `srvDo(path,body,after)` = api+applyBoot+after; `applyBoot(d)` заливает profile/requests/bookings626/verifQueue/users/dayload/busy626/favSets.
- `render()` сохраняет скролл и введённый текст (input/textarea с id) при перерисовке того же экрана; поллинг `startPolling()` — api('me') каждые 12 с (пауза при открытом overlay/фокусе в поле, перерисовка только при изменении данных).
- В Telegram (`IN_TG`): рамка скрыта, BackButton по шагам (`tgLeft`), высота по `viewportStableHeight`, тема из Telegram + ручной тумблер (`userToggleTheme`, localStorage `obor_theme` перебивает), профиль моков очищается, ФИО — с сервера.

Заблокированная категория просто показывается недоступной; блокировки категорий приходят с сервера (`catBlocks`) и применяются в `rebuildCatalog`.
- Каталог: `CATALOG_BASE` (из catalog.js) неизменяем; `let CATALOG` пересобирается в `applyBoot` через `rebuildCatalog(extraItems, catBlocks, removedItems)`. `escJs()` экранирует `short` во всех onclick (в каталоге есть кавычки в названиях!).
- Регистрация: сначала автоматический поиск по Telegram username в закрытом листе `люди`, затем поиск по ФИО (не менее трёх слов); найденный профиль заполняется из листа. При отсутствии совпадения/ошибке/дубликатах — ручная форма. В ручной форме, MB → минимум один отдел, СО/ССФ → минимум одна организация; чипы роли («Твоя роль») только для MB (активист/стажёр/production) — **СО/ССФ больше не чип**, ставится бэкендом автоматически, если MB не выбран (`regPayload()` шлёт `role:""`). Перед регистрацией — экран `SCREENS.manual` (методичка), ссылка на него безусловна и с экрана `rules` (и до регистрации, и после).

### Бэкенд (bot/main.py)
- Один процесс: aiohttp API + статика + aiogram-бот (polling) + scheduler-task. Авторизация — HMAC-подпись `initData` (декоратор `auth`), `touch_user` обновляет username/фото.
- Роли: `ADMIN_IDS`/`SENIOR_ADMIN_IDS` из .env (старший ⊇ админ). В списках — ЛИЧНЫЕ id (не чатов!), иначе уведомления о верификации летят в общий чат (есть warning в лог).
- Каждый мутирующий эндпоинт возвращает свежий `boot_payload(uid)` — фронт просто делает applyBoot.
- Статусы заявки: new→curator→approved→issued→ret→closed / rejected / canceled. `escalated=1` — проблемный возврат ушёл старшим (куратор не принимает, `return`+comment только для не-старшего). `uncurator` — снять кураторство (до закрытия). 626: new→approved→ret→closed / rejected / canceled.
